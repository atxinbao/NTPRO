产品说明 · 最终当前北极星

让同一个策略从 Backtest 走到 Demo，再进入真实 Live。

NTPRO 当前只聚焦量化策略闭环。用户固定一个策略版本，用历史数据回测，在沙盒环境验证实时运行，满足独立 Live 准入条件后连接真实账户和 Venue；三种模式共享策略逻辑、参数结构、订单语义、风险指标和证据格式。

Backtest：Rust 引擎已存在 Demo：单节点 Sandbox MVP 已冻结 Live：正式产品目标，当前未开放 当前真实订单权限为 false
一句话北极星 一个量化人员可以在同一个策略工作台中完成策略版本固定、Backtest、Demo、Live、跨模式比较和复盘，不需要理解 Supervisor、node、Axum 或 Rust 底层实现。
产品合同 同一个 Strategy + StrategyVersion 可以产生多个独立 Run。Backtest 使用历史回放；Demo 和 Live 由同一套实时节点语义承载，只替换数据源、执行适配器、账户、Venue 和运行授权，不复制策略代码。

产品说明 · 策略闭环

产品从一个策略版本开始，也回到下一个策略版本

研究、验证、运行和复盘使用同一身份链；切换模式不复制策略，也不丢失数据、配置和结果来源。

01创建策略定义策略逻辑、参数结构、数据需求和风险约束。
02固定版本保存不可变的代码、参数、数据引用和版本标识。
03Backtest在历史数据上执行确定性回放，检查交易与风险结果。
04结果比较比较不同版本和参数的收益、回撤、成交与稳定性。
05Demo同一版本进入 Sandbox，验证实时数据、订单语义和运行稳定性。
06Live 准入单独绑定真实账户、Venue、适配器、风险限额和人工授权。
07Live 运行在真实市场运行，并持续观察订单、成交、持仓、风险和健康。
08复盘迭代统一对比三种模式的结果，形成下一策略版本。
共享策略，不共享运行权限 Backtest、Demo、Live 使用同一个策略版本，但每个 Run 都有独立的模式、数据、配置、账户、Venue、时间范围、订单、成交、持仓、风险和证据。Backtest 或 Demo 通过不能自动开启 Live。

策略版本不可漂移

进入任何模式后，代码和参数快照保持不可变；修改必须生成新版本。

三种模式语义一致

订单、成交、持仓和风险使用同一领域模型，差异只来自数据与执行环境。

Live 独立授权

真实账户、真实 Venue 和订单发送必须经过单独准入，不能由回测收益或进程健康推导。

产品说明 · 三种模式

模式不同，策略资产和观察语言相同

产品使用 Backtest、Demo、Live 三个明确名称；代码中的 Demo 对应 Environment::Sandbox。

BACKTEST历史验证历史数据 + BacktestEngine + 模拟撮合；当前已有 Rust 底层能力，产品闭环待整合。
DEMO / SANDBOX实时验证实时或沙盒数据 + LiveNode + 模拟执行；当前单节点 MVP 已完成并冻结。
LIVE真实交易实时数据 + 同一 LiveNode 语义 + 真实适配器和账户；正式目标，当前未开放。

技术说明 · 系统拓扑

当前技术基线是本地单节点 Demo

代码入口为 nautilus mvp serve。一个进程内的 MvpRuntime 使用 SupervisorRegistryStore 注册并启动一个 ntpro-node，随后启动 Axum HTTP 服务提供两个门户。

1

CLI 入口

nautilus mvp serve 读取沙盒节点配置和本地工作目录。

2

Supervisor 存储

SupervisorRegistryStore 管理节点注册、进程状态、日志与指标文件。

3

单个节点

一个 ntpro-node 承载一个策略实例、一个沙盒账户和一个 Venue。

4

Axum 门户

同一 HTTP 服务提供机构工作台、控制中心和版本化 MVP API。

部署边界 当前没有远程 node agent、共享注册中心、多主机调度或自动故障转移。一个节点也不等于一套工作台；两个门户是同一运行实例上的集中视图。
三模式与代码的对应关系 Environment 已定义 Backtest、Sandbox、Live；历史回放由 BacktestEngine 承载，Demo 与 Live 共享 LiveNode 的实时运行语义。当前 CLI 只构建 Sandbox 节点，真实 Live 的适配器、账户、Venue 和订单权限尚未接入。

技术说明 · 运行链路

一次启动如何变成两个可访问门户

以下顺序直接对应 crates/cli/src/mvp.rs，描述当前代码行为，不是未来架构设想。

1

注册并启动

MvpRuntime::start 注册节点，再通过 start_node_process 启动子进程。

2

生成本地事实

写入 registry、identity contract、status contract、节点状态、指标和日志。

3

启动 HTTP 服务

run_dashboard_command 挂载门户静态资源、只读查询和受限 start/stop 动作。

4

持续刷新与退出

运行时定期刷新状态；Ctrl-C、服务错误或状态刷新失败都会进入节点停止流程。

默认启动参数 配置 configs/nodes/btc-ema-shadow.toml，工作目录 target/ntpro-mvp，节点 mvp-node-001，监听 127.0.0.1:5173。这些默认值定义在 crates/cli/src/opt.rs。

为什么必须拆成两个门户

机构用户围绕收益、风险、策略和交易结果工作；控制团队围绕审批、部署、凭证和系统健康工作。合并导航会模糊责任与告警优先级。

为什么策略仍在机构工作台

策略是投资资产，需要与组合、账簿、风险目标和交易结果连续呈现；独立审批与生产部署则必须留在控制中心。

为什么控制平面不是第三个产品

它只保存权威身份、状态、审批、事件和审计事实，并向两个门户投影；没有独立用户旅程，也不能成为第二套交易状态源。

为什么命令门禁必须独立

查询与操作承担不同风险；写命令必须经过独立授权、审批、风控、幂等和审计，不能由只读页面能力自动继承。

产品说明 · 推进路线

先做完整策略闭环，再扩展机构平台

既有 M0-M4 提供单节点 Demo 技术基线。下一阶段只围绕同一策略的 Backtest、Demo、Live 三模式产品化推进；真实 Live 是必达能力，但必须作为独立高风险阶段实现和验收。

Roadmap 判断标准 不是“有引擎、有命令或能启动节点”就算产品完成。用户必须能在策略工作台中创建版本、发起 Run、查看结果、比较模式、理解失败原因，并在明确准入后运行真实 Live。
S0
产品合同 · 下一阶段

策略、版本与运行资源

建立一个可贯穿三种模式的产品身份链，避免 Backtest、Demo 和 Live 各自形成孤立入口。

  • 固定 Strategy、不可变 StrategyVersion 和独立 Run 三层资源。
  • 统一参数、数据需求、订单语义、风险指标和证据格式。
  • 每个 Run 明确记录 Environment、适配器、账户、Venue、配置和结果。
退出条件同一 StrategyVersion 可创建三类 Run，身份、状态、来源和错误合同稳定；任何模式都不能修改已冻结版本。
S1
Backtest · 产品化

历史验证闭环

把已有 Rust BacktestEngine 从底层能力变成策略工作台中的完整用户流程。

  • 选择策略版本、数据集、时间范围、资金和模拟 Venue。
  • 展示运行状态、交易明细、持仓、收益、回撤、风险和日志。
  • 支持多个版本与参数 Run 的确定性比较和结果留证。
退出条件用户无需命令行即可完成创建、运行、查看、比较和复现 Backtest，结果可追溯到同一 StrategyVersion。
S2
Demo · 已完成

实时沙盒验证

将已经冻结的单 Supervisor + 单 Sandbox 节点接入同一策略工作台。

  • 直接选择通过验证的 StrategyVersion 创建 Demo Run。
  • 观察实时数据、信号、订单意图、模拟成交、持仓、风险和健康。
  • 把 Demo 与 Backtest 的行为和结果差异放在同一比较视图。
退出条件Demo 不复制策略代码；工作台可完整解释运行状态和模式差异，真实订单仍保持关闭。
S3
Live · 必达能力

真实交易产品能力

在同一 LiveNode 和 StrategyVersion 语义上接入真实数据与执行，不另建一套 Live 策略。

  • 建设真实 Venue 数据/执行适配器、账户绑定、凭证和连接状态。
  • 实现订单提交、撤改、成交回报、持仓对账、风险门禁和人工停机。
  • 建立 Live 独立准入、最小权限、幂等、审计、恢复和回滚证据。
退出条件真实账户和 Venue 在独立授权下完成受控端到端交易；异常、断连、重复回报和恢复场景 fail closed，并证明不会由 Demo 自动继承权限。
S4
三模式闭环 · 产品冻结

统一比较与持续迭代

让策略人员在一个工作台中判断历史、沙盒和真实运行之间的偏差，并形成下一版本。

  • 统一比较收益、回撤、滑点、成交质量、风险事件和运行稳定性。
  • 从任何结果追溯策略版本、数据、配置、账户、Venue 和证据。
  • 完成浏览器、性能、故障、操作手册、发布和回滚验收。
退出条件一个策略版本可在三种模式中独立运行并统一复盘，产品声明、页面能力和实际交易边界完全一致。

当前先做 S0

先固定策略、版本和 Run 合同，后续页面、API 和三种引擎接入才不会重复建模。

Live 不是 Sandbox 开关

策略代码相同，但真实数据、执行、账户、风控、授权和故障处置必须单独建设。

平台化后置

多机构、多节点、集中运维和复杂角色治理在策略三模式闭环完成后再独立规划。

展开已冻结的 M0-M4 单节点 MVP 历史路线
MVP 完成后的真实体验 研究员可以从一个策略版本和确定性回测结果追溯到运行实例；Supervisor 可以重复启停一个沙盒节点；交易员可以只读查看该实例的账户、仓位、订单、成交和风险；运维可以查看同一实例对应的节点健康、日志、指标和事件。
产品入口
机构工作台策略与回测摘要、账户、仓位、订单、成交、风险，只读
控制中心单节点注册、启动、停止、状态、健康、日志与指标
共享状态合同
稳定身份策略版本、回测、节点、策略实例、账户、Venue 与环境分别标识
统一证据来源、时效、错误、降级和事件编号在两个门户保持一致
运行闭环
一个 Supervisor管理一个本地沙盒 ntpro-node 的完整生命周期
一个节点承载一个策略实例，并绑定一个沙盒账户与 Venue

身份不能合并

node_id、strategy_id 和交易员工作空间分别建模；当前一对一只是 MVP 部署约束，不是领域等式。

状态不能混淆

进程存活、节点健康、策略状态、交易准备度和回测结果分别呈现；HTTP 成功不代表系统健康。

能力不能越界

MVP 保持沙盒和只读产品边界，不包含提交、撤单、改单、重试、自动恢复或真实交易。

展开完整验收维度

接口

接口验收

  • 数据模式与客户端开发包同源生成
  • 破坏性变更有迁移说明
  • 时效、错误和降级语义完整
  • 页面不读取未声明字段

行为

行为验收

  • 快照与增量流合并确定
  • 断线、乱序、重复事件可处理
  • 命令幂等且状态可追踪
  • 风险拒绝不能被页面绕过

证据

证据验收

  • 接口与增量流合同测试
  • 黄金轨迹与确定性重放
  • 关键页面截图与像素检查
  • 性能、可访问性与错误状态报告

产品

产品验收

  • 两个门户的核心任务分别闭环
  • 跨门户能力默认不可见
  • 机构范围与角色权限在服务端生效
  • 业务影响与技术根因可互相追踪

状态

状态验收

  • 研究、治理、准备度和技术健康独立
  • 接口成功不等于运行健康
  • 审批通过不等于自动部署
  • 回测完成不等于盈利或生产准入

发布

发布验收

  • 网页与桌面版本使用同一合同
  • 后端、开发包和页面版本可追溯
  • 升级与回滚路径经过验证
  • 发布声明不超过实际能力
