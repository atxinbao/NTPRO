机构产品信息架构 · 第八版

一个平台，两个门户，一个共享控制平面

产品按责任和决策类型分开，而不是为每个岗位建立独立系统。机构工作台服务投资与交易业务，控制中心服务独立治理与平台运行；策略状态、审批、部署和事件通过同一控制合同交接。

系统定义与目标用户 NTPRO 是面向量化自营交易公司、系统化对冲基金、做市和多策略交易团队的机构系统化交易平台。重点解决多策略、多账户、多交易场所下的研究验证、组合观察、执行监控、风险控制、生产运行和审计追踪；首期不承担基金会计、托管结算、客户报告等传统资产管理后台职责。
原则一按责任拆门户机构用户做投资、策略和交易决策；控制团队做审批、部署和系统治理。
原则二按对象组织业务组合、账簿、策略、账户和运行实例使用稳定标识，不以技术模块作为入口。
原则三一套事实，多种投影业务影响与技术根因来自同一事件，不复制交易状态机，不建立第三个门户。

栏目设计约束

不重复
左侧是产品域，顶部是正在处理的对象，两者不建立同名导航。
不串岗
节点、凭证、部署、恢复和技术根因不进入机构工作台一级栏目。
不失焦
切换策略、订单或风险对象时，账户、账簿和环境范围始终保留。
不误导
HTTP 成功、回测完成和审批通过都不能被显示为生产运行健康。
不越权
当前只允许查询和预览，真实交易操作继续由独立授权范围决定。

页面风格与样式定稿

沿用 project.html 原有的浅灰文档底色、炭黑框架和墨绿工作台层级，只吸收 Figma 参考中的布局关系，不替换项目既有视觉语言。

原有底色 / 炭黑墨绿 / 数据优先
风格结论 保持项目原有视觉基线。两个门户共享炭黑墨绿壳层、密度和交互规则，通过栏目与对象语义区分职责，不建立第二套配色。
层级深灰壳层、一级边框和稳定分区。表格、图表和对象详情优先，不使用嵌套卡片、装饰渐变或大面积品牌色。
色彩蓝色只表示选中与导航；绿色表示正常或正向；红色表示风险或拒绝；琥珀表示关注、陈旧或受限。
文字与数字中文使用系统无衬线字体；业务数字使用等宽或表格数字。标题紧凑，正文不承担操作说明书角色。
尺寸与密度桌面左栏约 152-164px，窄屏折叠为 56px；顶部范围栏 42px、任务页签 36px、状态栏 24px，控件圆角 3-4px。

共享控制平面的对象合同

两个门户通过稳定标识互相引用；层级、资产、运行和证据不是一棵被强行简化的树。

一套事实 / 两个角色投影
01 / 机构范围机构与交易台法律实体、交易台、账簿、组合和授权范围。
02 / 策略资产策略与版本负责人、逻辑、参数、数据绑定和变更记录。
03 / 验证证据回测与候选数据版本、配置快照、交易明细和审批申请。
04 / 运行绑定部署与账户策略版本、账户、交易场所、品种和运行模式。
05 / 业务事实组合与交易仓位、订单、成交、风险、对账和业务影响。
06 / 控制证据状态与审计节点、遥测、事件、审批、回执和变更来源。

申请 / 审批 / 部署 / 事件 / 审计

策略发布交接

量化研究员提交候选，模型审批人员独立复核，平台运维人员部署，机构用户查看生效结果。

机构工作台候选版本、回测证据、申请状态和退回原因。
控制中心审批证据、有效期、部署快照、回滚和审计。

运行事件交接

控制中心处理技术根因与恢复，机构工作台只呈现受影响账簿、策略和允许的业务动作。

机构工作台业务影响、准备度、降级状态和事件链接。
控制中心组件链、日志、指标、负责人、处置和回执。
第三版收敛结论 策略是机构工作台中的核心业务资产，但不是整个产品唯一入口。组织治理与系统运维必须独立进入控制中心；共享控制平面只连接身份、状态、审批和证据。任何前端实现都不得把后端能力、发布证据或接口成功误写成真实交易授权。

后端到双门户产品的交接

后端与产品前端之间还差什么

TTR-001/002 已解决治理接口挂载和原始事件存储隔离，但业务接口、机构身份和实时增量仍需独立产品化。

1

机构对象合同

固定机构、交易台、账簿、组合、策略、账户、部署和运行实例的标识与关系。

2

业务查询接口

把账户、仓位、订单、成交、风险、策略和回测投影成稳定、分页、可追溯的产品接口。

3

身份与数据范围

将角色、机构范围、环境和授权写入服务端合同，不能只靠前端隐藏菜单。

4

实时与交接

用快照和增量流承载业务状态，并用统一事件编号连接业务影响、技术根因和审计证据。

双门户与共享控制平面的目标框架

为什么必须拆成两个门户

机构用户围绕收益、风险、策略和交易结果工作；控制团队围绕审批、部署、凭证和系统健康工作。合并导航会模糊责任与告警优先级。

为什么策略仍在机构工作台

策略是投资资产，需要与组合、账簿、风险目标和交易结果连续呈现；独立审批与生产部署则必须留在控制中心。

为什么控制平面不是第三个产品

它只保存权威身份、状态、审批、事件和审计事实，并向两个门户投影；没有独立用户旅程，也不能成为第二套交易状态源。

为什么命令门禁必须独立

查询与操作承担不同风险；写命令必须经过独立授权、审批、风控、幂等和审计，不能由只读页面能力自动继承。

当前产品北极星

在单节点运行基线上完成产品 MVP

PR #1198 已交付一个 Supervisor + 一个节点的运行入口，MVP-003/004/005 已交付对象追溯、四轴状态和共享只读 API；当前只补齐双门户消费与最小界面。多节点平台、分布式调度、真实交易和完整门户能力不进入当前 MVP。

MVP 完成后的真实体验 研究员可以从一个策略版本和确定性回测结果追溯到运行实例；Supervisor 可以重复启停一个沙盒节点；交易员可以只读查看该实例的账户、仓位、订单、成交和风险；运维可以查看同一实例对应的节点健康、日志、指标和事件。

身份不能合并

node_id、strategy_id 和交易员工作空间分别建模；当前一对一只是 MVP 部署约束，不是领域等式。

状态不能混淆

进程存活、节点健康、策略状态、交易准备度和回测结果分别呈现；HTTP 成功不代表系统健康。

能力不能越界

MVP 保持沙盒和只读产品边界，不包含提交、撤单、改单、重试、自动恢复或真实交易。

验收合同

后续工作的验收体系

不能只用“页面打开了”作为完成标准。机构工作台、控制中心和共享控制合同必须分别通过用户任务、权限、状态语义和证据链验收。

接口

接口验收

  • 数据模式与客户端开发包同源生成
  • 破坏性变更有迁移说明
  • 时效、错误和降级语义完整
  • 页面不读取未声明字段

行为

行为验收

  • 快照与增量流合并确定
  • 断线、乱序、重复事件可处理
  • 命令幂等且状态可追踪
  • 风险拒绝不能被页面绕过

证据

证据验收

  • 接口与增量流合同测试
  • 黄金轨迹与确定性重放
  • 关键页面截图与像素检查
  • 性能、可访问性与错误状态报告

产品

产品验收

  • 两个门户的核心任务分别闭环
  • 跨门户能力默认不可见
  • 机构范围与角色权限在服务端生效
  • 业务影响与技术根因可互相追踪

状态

状态验收

  • 研究、治理、准备度和技术健康独立
  • 接口成功不等于运行健康
  • 审批通过不等于自动部署
  • 回测完成不等于盈利或生产准入

发布

发布验收

  • 网页与桌面版本使用同一合同
  • 后端、开发包和页面版本可追溯
  • 升级与回滚路径经过验证
  • 发布声明不超过实际能力

项目证据与验证结果
