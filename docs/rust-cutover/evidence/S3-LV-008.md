# S3-LV-008 - 交易所订单对账、人工撤单与部分成交恢复证据

Date: 2026-08-13
Executor: Codex
GitHub issue: #1302
Status: REVIEW_REQUIRED

## 实现证据

- 订单状态 schema v2 持久化 Venue order ID、原始数量、累计成交数量和剩余数量；成交事件与
  交易所读回只允许累计成交量单调推进，来源身份、数量或时间倒退会 fail closed；
- Runtime 复用官方 Binance Spot HTTP client 查询单笔订单，并只对双人确认的当前订单发送一次
  撤单；部分成交保留已成交数量，只撤销剩余部分，不补单、不改价、不扩大数量；
- 对账、撤单 request/attempt/result 均为单次不可变工件。attempt 已存在而 result 缺失时禁止
  网络重试，结果进入 `unknown_manual_review`；错误路径也不会创建新订单或恢复动作；
- 每份 Runtime 控制结果先追加外部单调审计锚点，再发布本地 result 和签名 receipt；本地结果与
  回执必须成对存在，外部 latest 与工作区 head 不一致时拒绝发布；
- Product API 将机构负责人撤单申请和操作员确认拆为不同角色端点；两者必须绑定同一来源订单
  快照。策略工作台只提供负责人申请，不提供操作员代签；
- OpenAPI、生成 SDK 和严格客户端投影对账、撤单、部分成交数量及控制结果。数量守恒使用
  `BigInt` 定点十进制比较，避免 JavaScript 浮点误差拒绝合法部分成交；
- 追加订单、改单、批量动作、自动重试、自动修复、自动恢复和补偿交易继续保持关闭。

## 独立审查修正

- Gatekeeper 在首个 PR head 上发现：交易所累计成交量可能低于本地来源快照；现已在 Runtime
  和 Product API 双层要求累计成交量只能单调前进；
- 已存在但缺少本地 receipt 的结果不再允许创建新的外部锚点。仅当外部 latest 已经精确锚定
  该结果且直接承接当前 workspace head 时，才允许补发本地 receipt；
- 已存在结果恢复前会完整验证 request、admission、StrategyVersion、订单身份、数量守恒、
  状态字段、错误字段和单次 attempt；来源状态漂移或工件缺失均 fail closed；
- 注入式 Venue 测试证明撤单流程只执行一次查询、一次撤单、一次读回；查询失败、重启中断、
  过期请求和交易所已终态均不会重试或发送额外撤单。
- 第二轮 Gatekeeper 发现已完成结果会被当前订单正常推进误判为来源漂移，且过期请求无法进入
  既有 attempt/result 恢复路径。Runtime 现以请求创建时持久化的 source-order snapshot 作为
  不可变基准，当前订单只执行身份和成交量单调推进校验；过期只阻止创建新 attempt，不阻止
  已有 attempt/result 恢复，也不会再次访问交易所；
- 第三轮 Gatekeeper 进一步要求中断恢复也必须先验证不可变源快照和当前订单，现已取消该绕过；
  Product API 与 Runtime 都拒绝 Venue order ID 被清空，并对 `cancel_confirmed`、终态/待撤单的
  `cancel_not_required_terminal_or_pending` 使用明确交易所状态白名单；
- 第四轮 Gatekeeper 发现控制请求 attempt 被误当作真实 Venue 撤单、API/客户端联合状态矩阵不够
  完整，以及缺失 Venue ID 的取消事件会清空既有身份。现新增独立的
  `execution-cancel-venue-attempt.json`：只在调用交易所撤单前写入，并绑定请求哈希；中断恢复和
  result 的 `cancel_attempted` 必须与该工件一致。终态查询不会伪称已撤单，取消事件也不会用
  `None` 覆盖已知 Venue order ID；
- Runtime、Product API、OpenAPI 和 TypeScript 客户端现使用相同 action/status/flag 状态矩阵，
  并将原始订单数量绑定 admission。`filled`、`expired`、`rejected` 等撤单竞态终态允许保留真实
  cancel attempt，但不能伪称 `cancel_confirmed`；跨 action 状态、数量或 Venue 身份漂移均拒绝。
- 第五轮 Gatekeeper 要求订单状态与 Venue attempt 在重启和投影边界双向一致，并指出客户端遗漏
  control admission identity。订单声称已尝试但 marker 缺失会在策略恢复和 Product API 两层拒绝；
  严格客户端也将 control admission ID 绑定到当前订单，相关反例已加入 Rust 和 Vitest。
- 第六轮 Gatekeeper 指出 marker 必须先于网络撤单写入，因此 marker 领先订单状态是合法崩溃窗口。
  策略重启现以验证后的 marker 单调推进持久订单状态；Product API 同样投影该事实，让既有控制处理器
  发布 `unknown_manual_review` 且不访问网络。订单声称已撤单但 marker 缺失、或 marker 无订单仍拒绝。
