## 实现结论

- Demo 页面分别呈现策略身份、节点状态和 Run 列表的验证状态，未验证或陈旧来源不会降级成
  空列表，也不会暴露创建入口；
- Demo 创建仅接受来源新鲜的 stopped 节点，或与服务端 `runtime_snapshot_is_stationary`
  语义对应的精确静态状态：`stopped + available + stale` 且原因必须同时且仅为
  `supervisor_process_not_running` 与 `node_status_timestamp_marked_stale`；额外、普通陈旧、
  错误或泛化未知原因继续 fail closed；
- Demo 创建、启动和停止 mutation 保持 `retry: false`，失败文案明确不会自动重复提交；
- Demo 生命周期错误使用统一产品错误语义，用户只能在核对状态后再次显式操作；
- Demo 创建会比较第一次已验证 record 与第二次 registry record，任何时间回退或晚于读取后
  真实观测时钟的 baseline 都会在写工件和 ownership 前 fail closed；Run 创建时间、ownership
  claim 与投影校验使用同一真实观测时钟；
- production 浏览器验收覆盖停止后刷新、同一 workspace 服务重启、冻结结果读取和终态不自动
  启动；
- Roadmap 已把 UPV1-003 标记为 Issue #1324 / PR #1329 已交付，并把当前阶段推进到
  UPV1-004。

## 根因与修复

并发状态刷新可能在 Demo 创建期间把 Supervisor record 的 `updated_at` 推进到请求开始时间之后。
旧实现先固定请求时间，再读取 Supervisor record，导致创建接口返回 201 后，首次读取立即因为
`claimed_at_unix_ms < supervisor_record_baseline_unix_ms` 而 fail closed。

修复后，第二次 registry baseline 必须不早于第一次已验证 record，也不得晚于读取完成后的真实
观测时钟。通过后，该真实观测时钟同时写入 Run config 和 Supervisor ownership，并继续作为
投影校验时间；未来 baseline 和时间回退都会拒绝，且不会留下 manifest 或 ownership。
