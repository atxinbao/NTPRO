## 实现证据

- Product API 新增 owner、risk、operator 三个独立审批端点，分别要求机构用户、风控和运维
  三种不能互相替代的会话；每份审批工件绑定同一 proposal SHA、角色权威、风险策略和失效时间，
  并各自取得外部单调锚点回执；三份审批齐全前订单准入保持 blocked。risk 权威来自
  StrategyVersion 来源绑定的 `[risk]` 配置，用户请求的最大名义金额只可收紧、不得超过权威上限；
  Run、StrategyVersion、账户、Venue、instrument、`LIMIT/GTC`、最长 15 分钟有效期任一漂移，
  kill switch 激活、重复准入或来源失效均 fail closed；
- 准入工件的原始请求哈希会重建校验，其工件哈希写入向前兼容的 Live Run state v2 扩展字段，并通过既有外部单调
  锚点形成 revision 2；普通 `start_market_data` 不得消费或继承该准入；
- `start_execution` 重新执行当前账户、可交易权限、来源与风险 gate 检查，再生成独立
  `[live_execution]` 配置，复用官方
  `BinanceExecutionClientFactory`，并把准入的逐品种最大名义金额写入 Nautilus `RiskEngine`；
  配置 SHA、admission SHA、manifest SHA 和 Runtime artifact root 写入 externally anchored `starting`
  状态；节点在注册执行客户端前验证签名回执及远端 latest，并用 compare-and-append 生成一次性
  Runtime claim。第二个并发 Runtime、重启或删除本地 claim 工件后的重放都会被远端 latest
  拒绝，手工 TOML 或改写配置不能绕过；
- admission 派生固定 Binance client order ID，`submission_requested` 在送入 RiskEngine 前持久化；节点
  在异步分发边界前保守标记 adapter send 可能已发生，崩溃后必须人工对账而不会错误声明未发送；
  重启严格读取既有状态并阻断重放，篡改状态或 client order ID 直接失败；
- `ProductionSingleShotExecutionStrategy` 只创建一个 `LIMIT/GTC` 订单，订单创建后立即关闭追加
  下单能力；真正构造订单前会再次检查准入失效时间，等待 instrument 期间过期则以
  `submission_failed`、`actual_submission_attempted=false` 终止；cancel、replace、自动重试和
  自动恢复均不可达；
- Runtime 写入严格的 `execution-order-state.json`，Product API 与工作台投影 waiting、submit、
  accepted/rejected/denied、partial/filled/canceled、expired 和失败状态；订单状态若出现在未消费准入、非运行生命周期、
  无 `[live_execution]` 配置、畸形或身份错配场景会阻断读取；
- manual stop、异常退出和停止重试从真实订单状态计算 endpoint/send/submitted 标记，停止工件绑定
  `execution-order-state.json` SHA，并随 terminal state 进入外部审计锚点；状态发布中断后会校验并
  复用完全一致的 `stop.json`，不会因 `create_new` 冲突而卡死；
- 本地 Runtime claim 字节必须与外部回执 `state_sha256` 完全匹配；工作台、机构门户、控制中心
  和 risk token 的启动输出由定向测试保证不会串位；
- OpenAPI、生成 TypeScript SDK、严格客户端和 Live 页面增加单笔提案与负责人确认；页面只代表
  当前机构负责人，不再代签风控或运维审批，并展示三方审批进度和订单生命周期结果；不提供撤单
  或改单按钮。
